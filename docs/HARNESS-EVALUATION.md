# Harness Evaluation Checklist

Generated 2026-09-12 by running the `harness-eval` skill (Tech Leads Club), Track A+B+C, against every
`extended/<skill>/` override in this repo plus the templates and local skills it surfaced.
Premise for this pass: the vendor (Tech Leads Club) skills these overrides sit on top of were freshly updated,
so the question for every row is whether the override/template still earns its place now that the base has moved.

This is a **checklist, not a changelog**. In `Overridden Skills` and `Templates` below, **one row is one
actionable item**, not one row per file — where a file's run surfaced more than one action, it's split across
multiple numbered rows (shared `#` and name) so each can be tracked and referenced independently; a file needing
no action gets exactly one `Rejected` row so it stays traceable. Work items one at a time, flip `Status` as you
go, and use `Description` + `How to Fix` + `How to validate` so a later pass doesn't need to re-run harness-eval
from scratch to remember why a row exists.

Raw run output for every row lives under `.harness-eval/runs/<run-id>/` in this repo (report-only; harness-eval
never auto-applies Ship/Slim/Mixed verdicts).

## Known tooling limitations (read before trusting a trap-FAILED row)

`harness-eval`'s calibration ("trap") plants and its deterministic fan-in scanner (`slim_fanin.py`) assume a
repo layout with `AGENTS.md` and `.agents/skills/` / `.cursor/skills/` / `.claude/skills/` skill trees. This
repo has none of those — it uses `CLAUDE.md` + top-level `skills/` and `extended/` — so:

- **Track B / Track C trap gates failed on several rows below** purely because the calibration plants cite
  paths that don't exist here, not because of anything wrong with the file being evaluated. A failed trap
  discards the Ship/Slim band for that run — those rows carry **uncertified** signal only, flagged as such.
- **`slim_fanin.py` itself returns zero citers even for files with real callers**, because its scan is
  hardcoded to `.agents/skills/**` / `.cursor/skills/**` / `.claude/skills/**`. Every run in this sweep worked
  around this by instructing judges to manually `grep` the real repo — but at least one run
  (`templates/test-execution-scope.md`) shows even manually-instructed judges can still undercount callers, so
  a Slim/Mixed verdict should always be independently spot-checked with a fresh
  `grep -rl "<template-name>" --include="*.md" .` before acting on it.
- **This document itself was incidentally read by judges** during at least one run (a caller-grep matched
  `docs/HARNESS-EVALUATION.md`). No verdict was actually changed by it so far, but future runs should
  explicitly exclude this file from judge greps/reads to avoid a judge cribbing a prior run's answer instead of
  deriving its own (see `Templates` item 16).

Until harness-eval's plant templates and fan-in scanner are adapted to this repo's actual conventions, treat
any Ship/Slim verdict on a trap-FAILED row as a lead to manually confirm, not a certified action.

## Glossary — what each column means

| Column | Meaning |
| --- | --- |
| # | Sequential reference number for one concrete action item within its table (`Overridden Skills`, `Templates`, `Skills`, and `Root Context Files` each number independently). Use this to point at a specific item in conversation. |
| Name of the skill / template | The `extended/<skill>/` override, `templates/*.md`, or `skills/<name>/` file this row's action item applies to. The same name repeats across consecutive rows when a file has more than one action item. |
| Status | `Pending` (not started) · `In Progress` (being worked) · `Done` (recommended action applied and validated) · `Rejected` (evaluated, consciously decided not to act — including "no action needed, file confirmed fine"). |
| Track A | Deterministic correctness check (harness-eval script, ~0 model tokens): do the paths/commands this file cites actually exist? Highest certainty of the three tracks. `—` when not relevant to this specific action item. |
| Track B | Redundancy check (dual LLM judges + calibration plants): would an agent already know this without the file (i.e. is it duplicated elsewhere in the repo)? Only certified (`Ship`) if the trap gate passed; a failed trap means "uncertified" — informative, not actionable on its own. `—` when not relevant to this specific action item. |
| Track C | Usefulness check (dual LLM judges + plants + fan-in): if this whole file were deleted, would agent behavior actually change? `Keep-core` = essential, `Slim` = compressible/removable, `Mixed` = partly each, `Hold` = judges disagreed or trap failed. Gated by a fan-in check for other files that hard-load this one. `—` when not relevant to this specific action item. |
| Bottom line | One-sentence statement of this specific action item, in plain language. |
| Description | Full narrative: the specific findings, quoted evidence (file:line where relevant), and reasoning — detailed enough that evaluating this row later doesn't require re-reading the original harness-eval run. |
| How to Fix | Concrete edit(s) to make to resolve this item — what to change, where, and to what. |
| How to validate | Concrete, mechanical steps to confirm the recommended action actually resolved the finding once `Status` moves to `Done`. |

# Harness Evaluation Checklist

Generated 2026-09-12 by running the `harness-eval` skill (Tech Leads Club), Track A+B+C, against every
`extended/<skill>/` override in this repo plus one template it surfaced (`templates/token-efficiency-rules.md`).
Premise for this pass: the vendor (Tech Leads Club) skills these overrides sit on top of were freshly updated,
so the question for every row is whether the override/template still earns its place now that the base has moved.

This is a **checklist, not a changelog** — every row starts `Pending`. Work items one at a time, flip `Status`
as you go, and use `Description` + `How to validate` so a later pass doesn't need to re-run harness-eval from
scratch to remember why a row exists.

Raw run output for every row lives under `.harness-eval/runs/<run-id>/` in this repo (report-only; harness-eval
never auto-applies Ship/Slim/Mixed verdicts).

## Known tooling limitations (read before trusting a trap-FAILED row)

`harness-eval`'s calibration ("trap") plants and its deterministic fan-in scanner (`slim_fanin.py`) assume a
repo layout with `AGENTS.md` and `.agents/skills/` / `.cursor/skills/` / `.claude/skills/` skill trees. This
repo has none of those — it uses `CLAUDE.md` + top-level `skills/` and `extended/` — so:

- **Track B / Track C trap gates failed on 3 of 5 rows below** (`docs-writer`, `tlc-spec-driven`,
  `token-efficiency-rules.md`) purely because the calibration plants cite paths that don't exist here, not
  because of anything wrong with the file being evaluated. A failed trap discards the Ship/Slim band for that
  run — those rows carry **uncertified** signal only, flagged as such in `Track B`/`Track C` below.
- **`slim_fanin.py` itself returned zero citers even for a file with 3 real callers**, because its scan is
  hardcoded to `.agents/skills/**` / `.cursor/skills/**` / `.claude/skills/**`. Any future run that trusts this
  script's output at face value (instead of having judges manually grep `skills/` + `extended/`) should treat
  its fan-in "PASS" as unverified on this repo.

Until harness-eval's plant templates and fan-in scanner are adapted to this repo's actual conventions, treat
any Ship/Slim verdict on a trap-FAILED row as a lead to manually confirm, not a certified action.

## Glossary — what each column means

| Column | Meaning |
| --- | --- |
| Name of the skill / template | The `extended/<skill>/` override or `templates/*.md` file this row evaluates. |
| Status | `Pending` (not started) · `In Progress` (being worked) · `Done` (recommended action applied and validated) · `Rejected` (evaluated, consciously decided not to act). |
| Track A | Deterministic correctness check (harness-eval script, ~0 model tokens): do the paths/commands this file cites actually exist? Highest certainty of the three tracks. |
| Track B | Redundancy check (dual LLM judges + calibration plants): would an agent already know this without the file (i.e. is it duplicated elsewhere in the repo)? Only certified (`Ship`) if the trap gate passed; a failed trap means "uncertified" — informative, not actionable on its own. |
| Track C | Usefulness check (dual LLM judges + plants + fan-in): if this whole file were deleted, would agent behavior actually change? `Keep-core` = essential, `Slim` = compressible/removable, `Mixed` = partly each (see `11-mixed-apply.md` for the KEEP/CUT split), `Hold` = judges disagreed or trap failed. Gated by a fan-in check for other files that hard-load this one. |
| Bottom line | One-sentence recommended action, in plain language. |
| Description | Full narrative: the specific findings, quoted evidence (file:line where relevant), and reasoning — detailed enough that evaluating this row later doesn't require re-reading the original harness-eval run. |
| How to Fix | Concrete edit(s) to make to resolve the finding — what to change, where, and to what. Left blank until worked. |
| How to validate | Concrete, mechanical steps to confirm the recommended action actually resolved the finding once `Status` moves to `Done`. |

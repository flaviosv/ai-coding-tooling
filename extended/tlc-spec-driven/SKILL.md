# tlc-spec-driven — ai-coding-tooling Extension

Read this file immediately after the parent `SKILL.md`. It **augments** the parent —
it never replaces it. Parent behavior stays in force except where this file overrides
a specific point.

## Planning Is Prioritized

For any **non-trivial** task (3+ steps or an architectural decision), plan before building:
run the parent's Specify → (Design) → (Tasks) flow and confirm the plan before writing code.
Do not jump straight to implementation for non-trivial work.

**Trivial changes keep the express lane.** A one-sentence change touching ≤3 files runs the
parent's quick-mode (Describe → Pre-Implementation Check → Implement → Verify → Commit). Plan
prioritization never forces full-pipeline ceremony onto quick-mode tasks — the parent's
auto-sizing still decides depth.

## Artifact Naming: `<TASK-ID>-<slug>`

Name every feature and quick-task directory `<TASK-ID>-<slug>` — a task identifier plus a short
kebab-case description — instead of the parent's bare feature name or `NNN-` counter:

- Feature → `.specs/features/<TASK-ID>-<slug>/` (e.g. `.specs/features/PROJ-42-user-auth/`)
- Quick → `.specs/quick/<TASK-ID>-<slug>/` (the `<TASK-ID>` takes the place of the parent's `NNN` sequence)

Ask for the TASK-ID when you don't have one. If the project has no task tracker at all, fall
back to the parent's native naming (`<slug>` for features, `NNN-<slug>` for quick tasks).

## Reference Extension Convention

This project ships reference-level overlays alongside the parent skill. **Whenever you
load a parent reference file `references/<X>.md`, immediately check for and load
`references.extended/<X>.md` from the skill root, reading it right after the parent
reference as an augmentation (never a replacement).**

Currently provided:

| Parent reference | Loads-after overlay |
|------------------|---------------------|
| `references/brownfield-mapping.md` | `references.extended/brownfield-mapping.md` |
| `references/coding-principles.md` | `references.extended/coding-principles.md` |

The overlay's sections add to, or refine, the parent's — apply both together. If a future
overlay is added under `references.extended/`, the same rule applies automatically.

## Codebase Docs: 8 Files (not 7)

The parent brownfield-mapping generates 7 files in `.specs/codebase/`. This project adds
an **8th**, `PIPELINE.md`, generated by the brownfield-mapping overlay (CI/CD, deployment,
release management). The full set agents load as session context:

`ARCHITECTURE.md`, `CONCERNS.md`, `CONVENTIONS.md`, `INTEGRATIONS.md`, `PIPELINE.md`,
`STACK.md`, `STRUCTURE.md`, `TESTING.md`.

`PIPELINE.md` is **skipped** when the project has no CI/CD configuration.

## Project Vision → PROJECT.md, not STACK.md

The codebase docs describe *what exists in the code*. A project's **vision, goals, target
users, and scope** belong in `.specs/project/PROJECT.md` (parent `project-init`), **not** in
`STACK.md`. When mapping a codebase, put stack/library facts in `STACK.md` and any
project-purpose/vision content in `PROJECT.md`.

## Decisions → STATE.md

This project does **not** keep separate ADR files. Record architecture/library/API
decisions as `AD-NNN` entries in `.specs/project/STATE.md` (parent `state-management`),
with Decision / Reason / Trade-off / Impact. Older entries archive per the parent's
size-management rule.

## CONCERNS.md Coexists With the Tech-Debt Ledger

`.specs/codebase/CONCERNS.md` (generated by mapping) is a **living, evidence-backed risk
snapshot** — tech debt, fragile areas, security gaps, performance/scaling limits, observed
during analysis. It is **separate** from `docs/TECH_DEBTS.md`, the permanent numbered
`TD-XX` ledger owned by the `tech-debt-report` skill (out of scope here). Do not duplicate:
CONCERNS.md is the onboarding/risk view; TECH_DEBTS.md is the durable tracked register.
When a concern is already a tracked `TD-XX`, reference it rather than restating it.

## Technical Design Docs → `technical-design-doc-creator`

**Overrides the parent.** The parent's description routes formal technical design docs to
`create-technical-design-doc` — **that skill does not exist** (no directory, registry entry,
or trigger anywhere). The actual installed skill is **`technical-design-doc-creator`** (Tech
Leads Club). When a task needs a formal Technical Design Document (TDD), invoke
`technical-design-doc-creator`; ignore the parent's stale `create-technical-design-doc`
pointer. The parent's own Design phase still covers lighter spec-style design notes inline —
reach for `technical-design-doc-creator` only when a full standalone TDD is wanted.

# STATE

## Decisions

### AD-001
- **Decision**: Remove GitHub Mode's per-cluster subagent dispatch and worktree-fetch-cherry-pick-back mechanism. Process every surviving cluster's items sequentially, inline, in whatever context is already running GitHub Mode — the outer dispatch that invoked this skill (`build-feature`'s own subagent, or a Batch Mode per-PR subagent), or, only for a live direct invocation with no outer dispatch already isolating it, one whole-run Haiku subagent (never one per cluster).
- **Reason**: A real APLYR-19 run (found via `session-evaluate`) proved this mechanism doubly broken: (1) a cherry-pick conflict got committed to the branch as a literal unresolved `<<<<<<<` marker, requiring a whole separate recovery subagent (~10.6M tokens, 8.7min stall) because nothing validated the merged composite state before replying/resolving/pushing; (2) the top-level agent, consumed by hand-resolving those conflicts (itself a violation of the "never implement a fix directly" guardrail this mechanism was supposed to enforce), never reached the reply/resolve step at all — it pushed 28 commits and reported "40 threads fixed, 0 blocked" while 0 of 41 GitHub review threads were ever actually replied to or resolved. Since `build-feature` and Batch Mode already dispatch this skill as one isolated subagent per invocation, the per-cluster isolation was a second, redundant layer recreating protection that already existed one level up — and that redundant layer is what produced both failures.
- **Trade-off**: Loses intra-PR parallelism across independent, unrelated clusters — a PR with many small unrelated fixes now processes them one after another instead of concurrently. Given individual review-comment fixes are typically small and fully specified by the thread, this is expected to cost some wall-clock time, not token/reliability cost of the prior mechanism's failure modes.
- **Date**: 2026-09-02
- **Status**: active

### AD-002
- **Decision**: Add a mandatory validation gate (new GitHub Mode step 6) — build/typecheck plus the tests covering every touched file, and a conflict-marker scan — after the fixing pass and before any GitHub write (reply, resolve, or push).
- **Reason**: Closes the same session's build-breakage half of the bug: step 5's per-item test runs each confirmed one fix in isolation but never the state left behind once every fix landed together. This is the one point in the flow where a wider-than-single-item run is warranted, and it doesn't contradict [Test Execution Scope](../../templates/test-execution-scope.md) for that reason.
- **Trade-off**: One additional build/test run per invocation with any commits — real cost, but bounded and the alternative (a broken build reaching GitHub) is strictly worse.
- **Date**: 2026-09-02
- **Status**: active

### AD-003
- **Decision**: Move `git push` earlier (new step 7, before reply/resolve, was step 7 after reply/resolve at old step 6) and add a mandatory post-resolve verification (new step 9) that re-fetches `reviewThreads` and confirms `isResolved: true` for every thread this run claims to have resolved, before the final report may count it as such.
- **Reason**: Directly closes the GitHub-side half of the bug: nothing previously checked that the reply/resolve mutations were even called, let alone that they landed. Pushing before replying also means a crash between the two leaves the remote branch already reflecting the fix, rather than resolved-looking threads pointing at commits that were never pushed.
- **Trade-off**: None identified — this is strictly additional verification with no new failure mode of its own.
- **Date**: 2026-09-02
- **Status**: active

### AD-004

- **Reason**: Same session-evaluate audit; part of a repo-wide retrofit applied to every skill in `skills/` that dispatches subagents.
- **Trade-off**: None identified.

### AD-005
- **Decision**: GitHub Mode step 5 requires every item to have **one determined remedy** before it's worked — an item whose fix is still an open design choice (several candidate approaches with no decision rule, a dependency swap, a shared-component change beyond the PR's diff) is marked **blocked** with the options named, not fixed in place. Added a soft per-item budget (~10-20 tool calls) as a signal the remedy wasn't actually determined, not a hard stop.
- **Reason**: A real APLYR-20 run (found via `session-evaluate`, after AD-001 was already in place) showed a step-5 item dispatched with "determine the best approach: either X, Y, or Z" ran 355 turns / 30.9M tokens at 60 output-tokens/turn before converging — AD-001 removed the 9-way parallel amplification of this cost, but nothing stops a single occurrence of it inside whichever context runs step 5 now.
- **Trade-off**: Some items that previously got auto-resolved via extended exploration now come back **blocked**, needing a human decision. Judged worth it: unbounded exploration on an underspecified remedy is exactly the failure mode AD-001 was already correcting for the cluster-fan-out case.
- **Date**: 2026-09-02
- **Status**: active

### AD-006
- **Decision**: Replace AD-001's delegation-depth rule — "no further dispatch unless you're a live direct invocation with no outer dispatch already isolating you" — with a mechanical test: any context executing this skill as a subagent (started via the `Agent` tool, for any reason) must never call `Agent` itself, period; only a root context that is not itself a subagent may wrap step 5 in one subagent. Also closed a specific fabrication variant: a script, draft, or plan describing a reply/resolve is explicitly called out as not counting as done — only an actual landed `gh api`/GraphQL call, confirmed by step 9's re-fetch, does.
- **Reason**: A real APLYR-23 run (`build-feature` → its one fix-review dispatch subagent) proved AD-001's self-classification judgment call unreliable one level deeper than tested: the dispatched subagent, despite being exactly the case AD-001 says should fix inline, decided it was instead the "live invocation" exception and spawned a second Agent; that second agent spawned a third to do the actual file edits, dropping the reply/resolve steps from its own delegated prompt in the process. The second-level agent then drafted correct reply text, wrote a shell script whose loop only `echo`'d each reply instead of calling `gh api` ("For now, just log what would be posted"), ran it, and reported all 26 findings "fixed & resolved" off its clean exit. Commits genuinely pushed; zero replies or resolves ever reached GitHub. Both failures are the same category AD-001–AD-004 already tried to close, recurring because the rule they relied on ("are you already isolated") requires the model to correctly infer its own dispatch history, which it did not.
- **Trade-off**: None identified — this is a stricter, unambiguous version of the same existing rule (delegation depth was already meant to be none for a dispatched subagent); no intended capability is lost, since a subagent electing to "re-wrap because it might be the live case" was never correct behavior.
- **Date**: 2026-09-04
- **Status**: active

### AD-007
- **Decision**: Stop instructing GitHub delivery and start executing it. GitHub Mode's reply/resolve step is now performed by a new script, `scripts/deliver.py`, which the model invokes with a `delivery.json` it composes: the script fetches a baseline, replies in batches, re-fetches to confirm each reply landed exactly once, resolves only the threads whose reply it confirmed, re-fetches again to confirm `isResolved`, handles GitHub's abuse-detection block, and prints a JSON result whose every count derives from those re-fetches rather than from what it sent, exiting non-zero when any intended outcome is unconfirmed. Step 8 now composes-then-delegates, step 9 reads the script's output, step 10 quotes its counts. `references/github-delivery.md` keeps the fetch query (still model-run at step 1) and reframes its write sections as documentation of what the script does; its stale "load at steps 1 and 6" header — pointing at a step number that changed in an earlier renumbering — is corrected. Six accumulated anti-fabrication guardrails were consolidated and the war stories duplicated between SKILL.md and this file were replaced by pointers here. Added six genuinely new rules: check a finding against the *requirement* behind the behaviour (spec/`CLAUDE.md`/PR body), not only against the code; resolve paths from the worktree root; a GitHub-Mode dirty-tree guard; stage by path, never `git add -A`; cite SHAs verbatim from tool output; and Example 1's hardcoded `go build ./... && go test ./...` replaced with a project-resolved command, since it contradicted step 6's own scoping rule and had been copied verbatim into a Python repo.
- **Reason**: Five real runs across four `session-evaluate` audits (PR #28, PR #29, PR #1, PR #2, plus AD-001's original) reported reply/resolve work that GitHub never received. AD-001, AD-003 and AD-006 each closed this by adding prose; each time it recurred in a new shape. Reading the file against the transcripts showed why: the rules were already there and were not the binding constraint. Line 27 mandated the re-fetch and told two war stories about skipping it; the mechanical no-nested-`Agent` rule ended in "full stop" and was violated two days after being written; `github-delivery.md` documented every correct mutation and was *never opened* in three of four runs. The failures were also positional — the code fixes always succeeded and the GitHub writes always failed, because delivery runs last, at peak context, after a long fixing pass. What did work, every time it was tried, was structural: the caller's independent GraphQL verification caught all five, and the one ad-hoc script an orchestrator wrote delivered 24 threads in 46 seconds on the first attempt. A script removes the step from model judgment instead of warning about it again, and cannot report a success it did not verify.
- **Trade-off**: Adds executable code to a skill (`skills/<name>/scripts/`), which this repo's `AGENTS.md` previously discouraged — amended in the same change, with `session-evaluate/scripts/session_metrics.py` as existing precedent. The script becomes a maintenance surface and a dependency of GitHub Mode: if it is missing or broken, delivery stops rather than silently degrading to hand-rolled mutations — deliberately, since silent degradation is the failure being fixed. It also narrows the model's latitude at step 8 to composing text, which is the intent. Whether the Haiku tier remains appropriate is now a separate question: the script covers the delivery failures, but the judgment failures found in the same audits (a finding applied against its own spec, invented outcome buckets, replies paired to the wrong thread from truncated previews) are untouched by it and are being assessed against measured evidence before any model change — resolved in AD-008.
- **Date**: 2026-09-06
- **Status**: active

### AD-008
- **Decision**: Two changes closing the question AD-007 left open. (1) `scripts/deliver.py` now performs a **coverage reconciliation**: its input gains a `skipped` map of `thread id -> reason`, and `threads` plus `skipped` must together account for every in-scope thread on the PR — in-scope meaning published (not on an unsubmitted review) and not already resolved, both determined by the script's own fetch. Any in-scope thread in neither map is reported as `unaccounted` and exits non-zero; a thread listed in both, or skipped with an empty reason, is rejected as bad input. (2) **Every `Agent` launch this skill makes moves from Haiku to Sonnet** — Batch Mode's per-PR runs and the live-invocation whole-run wrapper alike — and `build-feature`'s Step 12 wrapper, the dispatch site behind several of the audited failures, moves with it; `templates/subagent-models.md` is updated for all three, and its stale "per-cluster fix subagents" row (per-cluster dispatch was removed in AD-001) is corrected to name the wrapper that actually exists.
- **Reason**: AD-007 made delivery mechanical but left the *judgment* failures from the same four audits untouched: a finding applied against a requirement documented in the project's own `CLAUDE.md` (caller reverted four files), threads classified from `body[:150]` previews producing four replies that described a different thread's finding, invented outcome buckets, and 32 of 43 threads dropped from a report without mention. The last two are mechanisable and are now the script's job — it already fetches every thread, so reconciling that set against the delivery file costs nothing and makes silently dropping a thread impossible rather than merely forbidden. The first two are not mechanisable, which is what settles the tier: they are silent correctness regressions in the user's own product, the new guardrails against them are prose, and prose guardrails in this specific skill have a measured 0-for-5 record at the Haiku tier. Note also that the apparent evidence *for* Haiku was confounded — every Sonnet success in the audits was also handed the correct mutations verbatim in a hand-written prompt, so what was actually compared was "Sonnet with the right procedure" against "Haiku without it"; `deliver.py` now gives every tier the right procedure, dissolving that confound. The cost objection does not survive counting rework either: the Haiku runs cost 24.1M and 97.6M *including* the repair runs they forced, and AD-007 removes those repair runs, which bounds Sonnet's marginal cost in a way it was not bounded before.
- **Trade-off**: Higher per-run cost on every `fix-review` dispatch, including each PR in a Batch Mode sweep, where it multiplies. Accepted for the reasons above, and explicitly revisitable: with delivery now tier-independent, the next runs produce the first uncontaminated comparison this skill has ever had, and the tier should be re-decided on that evidence rather than left as settled. The reconciliation also makes the delivery file stricter — a run must now enumerate what it is *not* answering, not merely what it is — which is deliberate, since the alternative was threads disappearing between fetch and report.
- **Date**: 2026-09-06
- **Status**: active
